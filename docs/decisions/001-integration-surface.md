# ADR 001：集成面采用黑盒边界拦截，而非进程内 SDK 注入

- **状态**：已接受
- **日期**：2026-09-30
- **决策者**：项目组

## 背景

需求文档 v1.1 通篇没有定义"被测 Agent 到底怎么接进来"，而这个决定是整套架构的地基。文档同时承诺了两件互相冲突的事：

1. 「兼容性：支持 LangChain、LangGraph、CrewAI、AutoGen 四大框架」
2. 「适配云端常驻 Agent（LightVela 等）」「第三类用户是当前增长最快、测试工具最空白的群体」

文档实现篇 1.1 节给出的方案是"在 Agent 运行时注入 TimeProvider，拦截 sleep、定时任务、cron 调用"——这是进程内注入路线。

## 决策驱动因素

核实文档 v1.1 的市场依据后（Meta Muse、腾讯 LightVela、PERSIST 论文均为真实存在），发现一个文档没有意识到的结构性事实：

- **Meta Muse 运行在 Meta 的 Muse Secure VM 中**，有独立的 Sentinel 网络代理控制其联网权限，用户/测试者拿不到进程。
- **腾讯 LightVela 托管的 Hermes Agent 运行在腾讯轻量云的独立云实例中**，用户通过微信/QQ/飞书等消息通道与它交互，跨会话记忆以文件形式（`SOUL.md`、`USER.md`、`MEMORY.md`、`memories/`、`state.db`）持久化在用户专属云服务器上。

即：**文档新增的第三类用户（也是文档自称"增长最快"的群体），其 Agent 进程对测试者完全不可见。** 进程内 SDK 注入、monkeypatch `time.sleep`、注入 `TimeProvider` 这些手段，对这一类用户**一行代码都执行不了**。

这不是实现难度问题，是方案对该用户群体根本不可用。

## 考虑的方案

| 方案 | 框架中立 | 支持云端 Agent | 可做故障注入/熔断 | 结论 |
|---|---|---|---|---|
| A. SDK/回调注入 Agent 进程 | 否，每个框架适配一遍 | **否** | 是 | 否决为主路线 |
| B. **LLM 网关 + 工具出口代理（网络层）** | **是** | **是** | **是** | **采纳** |
| C. 纯 OTel 旁观采集 | 是 | 部分 | 否 | 不足，仅作补充 |

## 决策

**采用方案 B 为主路线，方案 A 降级为可选增强。**

1. **主路径（黑盒）**：被测 Agent 通过两个网络边界接入测试沙盒
   - **LLM 网关**：Agent 的模型调用指向网关的 OpenAI 兼容端点。网关是 Token 计数的唯一权威来源，也是硬预算熔断的执行点。
   - **工具出口代理**：Agent 的所有工具网络出口经过代理，默认拒绝，按声明放行到 Mock 服务。
2. **增强路径（白盒）**：仅对**自托管 + 用户可控进程**的 Agent，可选启用进程内 SDK/回调以获得更细粒度的状态可见性。此路径永远是可选，不是必需。
3. **进程内时间加速**（原文档的实现主线）降级为该增强路径下的一种手段，不作为通用能力。

## 后果

**正面**
- 同时满足"四大框架兼容"与"适配云端常驻 Agent"两项需求，这两项在原方案下不可兼得。
- 框架中立性成为真实护城河，而非文档里的口号——因为不依赖任何框架的内部 API。
- 与凭据代理天然是同一个组件（见 ADR 003），减少移动部件。
- 顺应"独立第三方对抗性验证"的定位：只有黑盒才能验证平台自带护栏的有效性。

**负面 / 需要接受的代价**
- 无法直接读取 Agent 的内部状态（消息列表、Graph 节点、记忆对象），只能从边界流量推断。记忆快照必须走"适配器 + 用户声明路径"（见 ADR 002 与 `docs/detectors.md`）。
- 网关需要对流式响应做 Token 计数，比读 Agent 侧的 `usage_metadata` 复杂。
- 被测 Agent 需支持自定义 `base_url`（主流框架都支持，但要写进使用前提）。

**待办**
- W1–W2 walking skeleton 必须验证：一个 LangGraph ReAct 仅通过改 `base_url` 即可被网关完整观测。
- 明确写出"不支持"清单：无法拦截 Agent 自身进程内的 sleep、无法读取未声明的记忆存储。
