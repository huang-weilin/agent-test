# ADR 004：时间加速只发生在边界上，且"世界走过了"是一个被测出来的前提

- **状态**：已接受
- **日期**：2026-09-30
- **决策者**：项目组

## 背景

> **编号说明**：需求文档里 `3.6` 出现了两次——第一部分的"功能需求 3.6"是**长时运行与主动行为评估**（场景 6），第二部分"核心模块设计 3.6"是**行为回归集**（场景 5）。本 ADR 说的是前者。回归集见 `src/sandbox/regression/`。

功能需求 3.6 的验收标准里，和这一节直接相关的是"能模拟长时间运行（时间加速），观察 Agent 的主动行为模式"。文档实现篇 1.1 节给的方案与 ADR 001 背景里那段是同一句：

> 在 Agent 运行时注入 TimeProvider，拦截 sleep、定时任务、cron 调用。

ADR 001 已经因为"云端常驻 Agent 的进程测试者拿不到"把进程内注入整条路否掉了，并把它降级为可选增强路径。但长时运行这件事本身仍然成立——**而且恰恰对云端常驻 Agent 最成立**：它们本来就是被定时器叫醒的、两次唤醒之间根本不在跑。所以这里要做的不是把 3.6 删掉，而是把它重新表述一遍。

## 决策驱动因素

把"时间加速"这个词拆开，会发现它混了两件事，而混起来之后两件都做不对：

1. **让被测 Agent 觉得时间变快了**——需要改它的进程，ADR 001 已否，且对云端 Agent 不可能。
2. **让世界（目标系统）在过去很久之后的样子呈现给下一次会话**——只需要改边界上的东西，而边界完全在我们手里。

第 2 条才是长时运行真正需要的东西。被测 Agent 在两次会话之间本来就不在跑，它醒来时看到的世界（订单逾期没有、上一次扣款是什么时候）是"过了多久"的**全部证据**，而那些都在边界上。

同时有三个必须守住的性质，否则加速会静默地毁掉结论：

- **世界必须自洽。** 工具说"现在是三天后"，而报告里记的时刻是刚才，Agent 就在一个自相矛盾的世界里做决定，基于它得出的每一条结论都是垃圾——而报告照样长得正常。
- **加速器必须自检。** "场景声明隔了一天"和"引擎真的拨了一天"是两件事。前者是输入，后者是事实。加速器坏掉之后世界停在原地，检测器照样给出一份看起来正常的报告，读的人以为"Agent 隔了一天还是这么干"，实际上什么都没测到。
- **真实时间与虚拟时间不能互相替代。** 真实时间决定"哪一次运行更晚"（回归集靠它排序）、一次运行花了多久；虚拟时间只描述被模拟的那个世界。混用会让一次模拟三个月的运行排到所有真实运行后面去，而它其实只是刚才跑的。

## 考虑的方案

| 方案 | 对云端 Agent 可用 | 世界自洽 | 结论 |
|---|---|---|---|
| A. 进程内注入 TimeProvider / 拦 sleep、cron | **否** | —— | 否决（同 ADR 001） |
| B. **边界上的虚拟时钟，mock 与报告共读同一个** | **是** | **是** | **采纳** |
| C. 真的等（sleep 30 小时） | 是 | 是 | 否决：回归集跑不动 |

## 决策

**采用方案 B：一个进程级虚拟时钟，所有的时间读数都从它出发。**

1. **一条纪律：一个时钟。** mock 的时间戳、订单的 `as_of`、扣款流水的 `created_at`、报告里的会话时刻，全部只读 `sandbox.clock.clock` 这一个对象。边界两侧各读各的钟，就是上面那条"世界不自洽"。
2. **默认是真实时间。** 没有长时运行时 `now()` 就是真实 UTC 现在，读它和读 `datetime.now(UTC)` 语义等价。默认路径一点没变，既有代码一行不用改。
3. **`advance()` 立即返回。** 这就是"加速"的全部：声明一段时间过去了，没有任何东西真的睡那么久。虚拟期间的真实耗时单独统计，与模拟跨度并列写进报告（"模拟跨度 1.2 天，真实耗时 17.3s（约 6238 倍）"）。
4. **只往前走。** `advance` 拒绝负值。往回拨一下就能让一件已经逾期的事重新变得不逾期，而报告上完全看不出来。
5. **"世界真的走过了"进入前提判定。** 一段会话的前提从"脚本跑完或被熔断"扩展为"**且**世界时钟恰好走到了场景声明的位置"。声明 30 小时、观察到 0 秒 → 前提不成立，结论不算数。这是加速器的自检，不是对被测对象的判断。
6. **只对声明了间隔的场景启用。** `after_gap_s` 全为 0 的场景不是长时运行，`result.clock` 为 `None`，报告里不出现任何虚拟时间的说法——否则读的人无法区分"这次没模拟时间"和"这次模拟了 0 秒"。

## 后果

**正面**
- 长时运行对云端常驻 Agent 可用，而它们正是最需要它的一类（也是文档自称增长最快的一类）。
- 加速器坏掉会**响亮地失败**：扣款笔数对不上，同时前提判定亮红灯，两道独立的信号。一个坏掉之后仍然报"通过"的长时运行比没有长时运行更坏。
- "世界会随时间变化"变成可证伪的：`tests/test_long_run.py` 内联构造的对照只有一个字段不同，结论必须相反。两者给出同一结论就说明那个"通过"是假阳性。

**负面 / 需要接受的代价**
- **不支持清单**（写进 `docs/longrun.md`，且不假装支持）：
  - Agent **自身进程内**的 sleep、cron、定时任务不受影响，仍是真实时间。
  - 因此一个内部按真实时间排程的 Agent，在长时运行里的表现与它在生产上被定时器叫醒时**并不相同**。这是黑盒的固有代价，不是实现遗漏。
  - 跨会话记忆的"内容随时间老化"测不到——记忆的写入与读取都在 Agent 进程那一侧，不在边界上（见 `docs/detectors.md`）。
- 虚拟时钟是**进程级状态**，与 `settings.tool_upstream_base_url` 一样，使"一次只跑一个运行"从约定变成必要约束（`docs/ui.md` 第 2 条）。跑完必须 `reset()`，泄漏的后果不是这次运行报错，而是下一次带着上一次的时间偏移跑，报告里每一处都正常，每一处都错。
- 跨会话的重复调用不再是"循环"。按会话切开之后 `loop.strict` / `loop.ping_pong` 不会误杀跨会话的正常行为，代价是真正的跨会话失控只剩 `loop.cross_session` 一条 warning 兜着——它**不**触发熔断。见 `docs/longrun.md`。

**待办**
- 真实模型接入后，`advance` 的量级要与模型的上下文窗口对齐（模拟三个月不会让模型的上下文里多出一天的对话，多出来的只是目标系统的状态）。
- 虚拟时钟目前只被 mock 与报告读取；真实上游接入时，网关侧也要读它，否则同一个"世界不自洽"问题会从另一侧回来。
