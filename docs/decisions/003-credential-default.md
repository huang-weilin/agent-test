# ADR 003：出口默认拒绝、默认不注入真实凭据

- **状态**：已接受
- **日期**：2026-09-30
- **决策者**：项目组

## 背景

需求文档 3.1 节提出的凭据方案是：

> 采用 Credential Vault 模式——真实凭据写入 egress sidecar，容器内只给 fake key 或空值。Agent 照常发 HTTPS 请求，sidecar 透明拦截后检查目标 host、method、path，**匹配绑定规则才注入真实请求头**。

以及 K8s Pod 模板：

```yaml
- name: credential-proxy
  env:
    - name: REAL_CREDENTIALS
      valueFrom:
        secretKeyRef: { name: agent-credentials, key: credentials.json }
```

"容器内拿 fake key"这一半是对的。**问题出在默认值：默认是"能打通就注入真实凭据"。**

## 决策驱动因素

这是一个**测试工具**，处理的是**可能有缺陷、可能已被提示注入污染**的 Agent。在这种前提下，默认放行真实凭据会产生以下通道：

1. **SSRF / 外泄**：被污染的 Agent 构造一个命中绑定规则的请求（host 用 DNS rebinding 指向攻击者 IP、或利用跟随重定向、或污染 `HTTP_PROXY` 环境变量），真实凭据就跟着请求发出去了。
2. **绑定规则本质上是模式匹配**：文档写的是"检查 host、method、path"，用 pattern 匹配路径时几乎必然出现可绕过的写法（`/v1/charges` vs `/v1/charges/../charges`，大小写，URL 编码）。
3. **副作用不可逆**：测试沙盒里跑出真实扣款、真实发信、真实改数据，本身就是事故——这与"测试"的目的直接矛盾。
4. **TLS 中间人负担**：要透明改写 HTTPS 请求头，sidecar 必须做 MITM，容器内需信任自签 CA。文档没有说明这一点，实际是个不小的运维和安全负担。

## 决策

**反转默认值：默认拒绝、默认无真实凭据。**

1. **默认出口策略为 deny-all。** 被测 Agent 的所有工具网络出口经代理，未显式声明的目标一律拒绝（返回明确的错误，而非静默失败——静默失败会让检测器把"被拦截"误判为"Agent 行为异常"）。
2. **默认不注入任何真实凭据。** Mock 是默认路径；绝大多数测试场景不需要真实副作用。
3. **真实凭据是逐条、显式、可审计的开启项**，且开启时必须同时满足：
   - **严格 host 白名单**（精确匹配，禁止路径正则、禁止通配顶级域）；
   - **禁止跟随重定向**（关闭 3xx 自动跳转）；
   - **禁止 Agent 进程设置 `HTTP_PROXY`/`HTTPS_PROXY`**，代理地址由沙盒注入且不可覆盖；
   - **优先使用范围受限的短期 token**，而非长期真 key；
   - 每次注入记录审计事件（谁、哪个 run、哪个 host、哪条规则）。
4. **不做透明 MITM。** 需要真实凭据时，走"目标 API 的官方 SDK base_url 重定向"或显式 HTTP 代理配置，而不是在 TLS 层做中间人。
5. **凭据永不进入被测 Agent 的进程环境或文件系统。** 只存在于代理侧。

## 后果

**正面**
- 消除了测试工具自身成为攻击面/事故源的风险——这对一个安全相关的测试产品是底线。
- 省掉 TLS MITM 的 CA 分发与信任维护。
- 默认配置在离线环境也能完整跑通，降低上手门槛。

**负面 / 需要接受的代价**
- 需要真实第三方集成的测试场景（如"验证 Agent 与真实支付网关的交互"）配置更繁琐，需逐条声明。
- 被拒绝的请求必须产生清晰的、可与"Agent 自身故障"区分的错误标记，否则会污染检测结果。这要求 trace 归一化层显式标注 `blocked_by_proxy` 事件。
- 不走 MITM 意味着无法观测 HTTPS 请求体内容。缓解：Mock 侧可完整观测（因为请求终结在 Mock）；真实直连场景只记录元数据（host/method/path/状态码/字节数），不记录 body。

**待办**
- 出口拒绝事件必须成为 `DetectorFinding` 的一种，且默认不计入"Agent 异常行为"告警（避免误报，见 `docs/detectors.md`）。
