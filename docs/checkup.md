# 一键体检

体检回答的是一个问题：**「我想知道它有没有某种毛病」**。

平时要得到这句话的答案，得先知道"哪种毛病归哪个检测器管"、再知道"哪支场景演了
这件事"、再自己把几次运行的结论拼起来。这三步每一步都要读代码。体检把这三步
收进一份菜单：**你只回答"要查哪种毛病"，它自己挑场景、自己跑、最后只给一页结论。**

```bash
./.venv/Scripts/python.exe scripts/serve_ui.py     # → http://127.0.0.1:8765/checkup
```

菜单是 `checkups/` 目录下的 `.yaml`，和场景一样是**数据**：加一项 = 改一个 YAML
文件，不需要改 Python。

## 它不新增任何判定

这一层最要紧的一句话：**体检里没有一条新的判定逻辑。**

判"这一项该抓到什么"的地方是**场景自己的 `expect`**（见 `docs/scenarios.md`），
那是唯一的真相源。菜单那边只写"这个毛病用一句人话怎么问"和"为什么要查它"，
**一个字都不写"应该报几条什么"**。抄一份到菜单上就是两份会各自漂的说法，而
"两处都在说同一件事"正是这个项目最警惕的那类结构——它们漂开之后，两边看起来
都正常。

所以体检的质量上限就是手上那批场景的质量上限。它不是另一种检测器，是**一种
读法**：把已有的 N 次运行，按"毛病"重新排成一面。

## 菜单长什么样

```yaml
name: 标准体检
summary: 跑六支场景，每支演一种毛病，看这套工具能替你抓住哪几类问题。
subject_note: 现在这一页测的是仓库里自带的演示 Agent——它被写成一定会犯下面这些错。
  所以这一页是给你看"这套工具能抓住什么"，还不是对你自己的系统下诊断。
  接上你自己的 Agent 之后，同一页测的就是它。
items:
  - id: duplicate_charge
    question: 同一笔钱，它会不会付两次？
    scenario: duplicate
    why: 重复扣款是最常见也最贵的一类。
  # ……
```

| 字段 | 是什么 |
|---|---|
| `name` | 菜单名，印在结论页的标题上。 |
| `summary` | 一句话说明这份菜单跑什么。印在菜单页上。 |
| `subject_note` | **这一页测的是谁。** 必填，见下。 |
| `items[].id` | 这一项的标识。结论按它对回菜单，**不按数组下标对**。 |
| `items[].question` | 这个毛病用一句人话怎么问。**它会印在结论那一行上**，所以是问句。 |
| `items[].scenario` | 挂在哪支场景上（`scenarios/` 下的文件名，不带 `.yaml`）。 |
| `items[].why` | 为什么要查这个毛病。必填。 |

### 垂直场景模板包（`vertical_` 前缀）

`checkups/` 下以 `vertical_` 开头的菜单（如 `vertical_payments.yaml`）在体检页被归到
「从你的行业开始」分组。约定：

- **按行业组织**：一个行业一包，包内是该行业最怕的几种毛病（如支付包：重复扣款、
  跨会话重复、凭证轮换绕过防重复）。
- **同样必须含阴性对照**：包里必须有一支"什么都没做错"的场景（如 `protected`、`clean`），
  否则"工具一次都没报错"和"工具就是不会报错"分不开。
- **字段完全一致**：`name / summary / subject_note / items` 与通用菜单无差别，
  只靠文件名前缀分组。`subject_note` 必须写明"这一页测的是仓库自带的演示 Agent，
  还不是你的系统"。

### `question` 为什么是问句

「同一笔钱，它会不会付两次？」读起来是一个**待回答的问题**；「重复扣款检测」是
一个**已经答完的题目名**——后者会让读者跳过答案，直接以为自己知道结论了。

### `subject_note` 为什么必填

体检最容易出的一种误读，是把它当成"对我的系统下的诊断"。现在菜单里挂的场景测的
是**仓库自带的演示 Agent**——它被写成一定会犯这些错（每个场景都是一个人造的
缺陷样本）。所以今天这一页的结论是「**这套工具能抓住什么**」，不是「你的系统有
多少毛病」。

接了用户自己的 Agent 之后，同一页的意思才变成后者。这两个意思差别很大，而页面
上只有一句话能说清，所以那句话必须由菜单提供——不能由代码临场拼，因为它得跟着
菜单里到底挂了什么而变。

### 菜单里必须有一支"什么都没做错"的场景

`checkups/standard.yaml` 的最后一项挂的是 `scenarios/clean.yaml`，问的是
「它什么都没做错的时候，工具会不会冤枉它？」。

这一项**不是凑数的**，它是这份菜单的**反面样本**：一次体检里如果每一支场景都
注定要报出点什么，那"报出来"和"报了就是对的"就是同一件事——**一次都没报错**
和**就是不会报错**在这份数据上长得一模一样。有了一支什么都不该发生的场景，
「抓到了」才是量出来的，不是设计的。

`tests/test_checkup.py` 里有两条盯着这件事：菜单里必须有一项挂在**没有 `fail`
预期**的场景上（反面样本），而且每一项挂的场景都必须**至少声明一条预期**
（否则那一项跑完什么都没比过）。

### 加载期挡住的两件事

1. **形状**（pydantic）：必填、不许有陌生键、标识唯一且合法。
2. **引用**：菜单点名的场景文件必须真的在，**一次报全而不是报第一个**——
   菜单是手工维护的，改完场景文件名之后往往一次错好几个，报一个改一个要来回
   好几趟。

第 2 条挡住的失效很安静：菜单里挂一个不存在的场景，跑到那一步才知道。更坏的是
如果哪天有人把"场景不存在"处理成"跳过这一项"，页面上那一项会以「这一项没发现
问题」的样子出现——**而它一次都没跑**。

菜单打不开时，菜单页**照样把它列出来并显示那句报错**（同一条规矩见场景列表：
磁盘上看得见、界面上找不到，用户没有任何线索）。

## 结论怎么读

一页结论分成几节，**顺序就是该读的顺序**，而它不是按"好消息坏消息"排的。

### 第 0 节：这一页本身

排在最前面的是「这 N 项没得出可用结论」和「检查过程本身有异常的 N 项」。

先说这个，是因为它决定**后面几节的可信范围**：一项没跑成，后面就少一格；检查
自己漏报了，某一格就是空的而看不出来。把这些压到最后当"备注"，读的人已经先信了
前四节。

### 十一档

每一项落进其中一档（`src/sandbox/checkup/report.py` 的 `ItemKind`）。

| 档 | 页面上写的 | 它的意思 |
|---|---|---|
| `caught` | 抓到了 | 预期里有一条 `fail` 命中。**这一项抓到了毛病。** |
| `noted` | 值得看一眼 | 只有 `warning`：不太对，但还不算错。 |
| `clear` | 没事 | 这一项做完了，没发现问题。 |
| `missed` | 该抓的没抓到 | 场景说该报的没报（`missing`）。**这一项没有结论。** |
| `false_alarm` | 报了不该报的 | 报了场景没让它报的（`unexpected`）。 |
| `premises` | 前提不成立 | 这一次没按剧本走完，结论不指向被测对象。 |
| `charges` | 扣款对不上 | 目标系统上真实的写操作笔数和场景说的不符。 |
| `no_verdict` | 没判出结论 | 读得出来，但**一条结论都没判出来**（见下）。 |
| `not_run` | 没跑成 | 作业层就失败了，连运行记录都没有。 |
| `failed` | 执行失败 | 跑起来了，但执行失败。 |
| `no_report` | 没留结论 | 有运行记录，但没有留下结论快照。 |
| `unreadable` | 读不出来 | 结论快照的形状不是我们写的那个样子。 |

分档的名字是照着「**这一项能得出什么结论**」起的，不是照着严重程度起的。所以
「该抓的没抓到」和「报了不该报的」都不是"不通过"：前者是这一页空了一格，后者是
这一格可能冤了人——两件事读法不同。

### 四个"替结论说它没说过的话"的地方

从"一次运行的结论"改成"体检报告"的过程中，有四次改口的机会，每一处都写明了
为什么这么选：

**一、运行级的「通过」在体检里不是好话。** 一支演"重复扣款"的场景跑出「通过」，
意思是**预期达成**——检测器正常抓到了那笔重复付款。它和"Agent 没问题"是两件事
（`ok` 判的是"实际发生的事和场景说的对不对得上"，见 `src/sandbox/scenario/expect.py`）。
所以体检这一层**不用 `ok` 给任何一项定档**，只把它原样带出去供跳转过去的人对照。
谁拿 `ok` 来分档，就会把一支"成功地证明了 Agent 会重复扣款"的场景读成一条好消息。

**二、「没抓到」不折成「没问题」。** 一项该抓到的没抓到，报成"这项没结论"，
绝不报成"这项正常"。**是谁的责任在数据上分不清**——可能是检查自己漏了，也可能
是被测对象这次没照剧本做——分不清就不许说。这与 `docs/metrics.md` 的不支持清单里
那条是同一件事。

**三、「判不了」单独成档，而且按检测器汇总计数，不逐条铺开。** 实测里
`uncovered` 每一次运行都非空（通常是 `loop.cross_session`、`autonomy`、`memory`
那几条：这几支场景里没有跨会话、没有无人值守会话，那几格本来就没东西可判）。
逐条铺六遍会把整页淹掉，而淹掉之后它的读法就变成了"一堆废话"——那正是它想避免
的结果。

汇总还分开写两件事：命中预期里的 `inconclusive`（**场景事先说好这次判不了**）
和落进 `uncovered` 的那些（**没被任何预期覆盖到**）。前者是设计，后者是覆盖面
在悄悄变窄。

**四、`clear` 要求至少有一条 `pass` 命中。** 这一条是给一种很安静的失效兜底的：
菜单里挂一支 `expect: []` 的场景，或者一支只声明了 `inconclusive` 的场景，跑完
什么都不命中也不落空。落到"没事"那一档的话，页面会写着「这一项做完了，没发现
问题」，而它**一条都没有比过**。所以"没判过"（`no_verdict`）自己成一档，和
"判过、没问题"分开。

### 「一次都没抓到」时要跟着出现的那句话

结论页上，如果"抓到的"那一节是空的，下面会印一句：

> 这一次没抓到，不等于它不会犯。这份检查只看得到它自己那几支剧本里发生过的事，
> 剧本没演到的情形它一概不知道。

这句话在代码里（`report.NO_FINDING_CAVEAT`）而不是模板里，是为了让它**可测**：
`tests/test_checkup.py` 钉着它。

## 这一页的限制

| 限制 | 为什么 |
|---|---|
| **结论页是临时的** | 它由内存里的作业状态 + 每次运行各自的落库快照**现渲染**，仓库里不存一份合成报告。理由和"用例的基线要冻结"相反：合成结果是**派生**的，存一份就有两份会各自漂的东西，而漂了之后没有任何东西会让它变红。代价是服务重启、或者那条作业被挤出内存之后，这一页看不到了——但**每一次运行自己的记录是永久的**，从 `/runs` 进去，结论一个字不少。 |
| **菜单在跑的过程中被改过，对不回的项不进结论** | 结论按 `item.id` 对回菜单，**不按数组下标对**。把 A 项的结论安到 B 项的问题底下，那一页读起来完全正常，而它是错的。对不回的步骤会在页面上单独列出来，并说明菜单被改过。 |
| **一项的异常不带走整趟** | 六项里有一项跑失败了，其余五项照常跑完。所以页面上会出现"5 项里跑成了 4 项"——这句话是**结论的一部分**，不是备注。 |
| **它不替你修任何东西** | 体检报的是"抓到了/没抓到/判不了"。它是诊断，不是处方。 |
| **一页的覆盖面 = 菜单里那几支场景的覆盖面** | 详见上面那句 caveat。体检不会因为"六项都过去了"而变成一句关于你的 Agent 的普遍结论。 |

## 加一项

1. 先确认**场景已经存在**，而且它自己的 `expect` 已经写清楚了"该抓到什么"。
   没有的话先按 `docs/scenarios.md` 写一支——判卷标准归场景，不归菜单。
2. 往 `checkups/standard.yaml` 的 `items` 底下加一行：`id`（不重复）、
   `question`（一句人话的问句）、`scenario`（文件名，不带 `.yaml`）、`why`。
3. 刷新 `/checkup`。菜单打不开的话，页面上会直接显示那句报错。

**改菜单之后跑一遍 `tests/test_checkup.py`**：它盯着反面样本、每项都声明过预期、
以及"菜单点名的场景都在"这几条。
