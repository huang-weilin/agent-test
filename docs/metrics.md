# 指标看板（需求 3.7）

```bash
./.venv/Scripts/python.exe scripts/serve_ui.py    # → http://127.0.0.1:8765/metrics
```

需求那一行是「指标看板 | 展示通过率、成本、延迟等核心指标」。这一页管**横着比**：
最近这批运行稳不稳、慢在哪、不通过的都是因为什么。它**不**回答另外两个问题——
单次运行怎么样（看 `/runs/{id}`）、长期花了多少（看 `/cost`）。

口径全在 `src/sandbox/metrics.py` 里，这一页只是把它渲染出来。

## 一、那个数不叫「通过率」

需求写的是"通过率"，交付出来叫**预期达成率**。这不是回避，是因为叫「通过率」
的那一版会说出比观测多的话。

`ScenarioResult.ok` 的判据是四条同时成立：执行没出错、前提成立、目标系统侧的
扣款对得上、场景写下的预期达成。它回答的是

> 这次运行的结果，和场景里写下的预期一致吗。

而「通过率」这三个字会被读成

> 这个 Agent 有多少比例的运行是合格的。

两者不等价，差在一次未达成的**成因**上。未达成有两种方向相反的来源：

| 成因 | report 里的样子 | 通常意味着 |
|---|---|---|
| 出现了没被任何预期覆盖的 fail 结论 | `expectation.unexpected` 非空 | 被测对象做了一件我们没料到的事 |
| 预期没命中 | `expectation.missing` 非空 | **我们预料它做的那个错没出现** |

第二种常被忽略。一个"预期循环、结果没循环"的运行，在这页上是不通过——但它多半
说明用例要改（或者检测器漏报了），而不是产品有缺陷。

要分清"Agent 真的没犯错"和"检测器没报出来"，缺的那块信息是**脚本消费量**：脚本被
完整消费 = Agent 确实做了那些事，那时"检测器什么都没报"就只能解释成漏报
（`scenario/expect.py` 的模块注释把这条写下来了）。但**这一页没有做这条推断**——
`script_steps_consumed` 在报告快照里，可把它变成一句结论是需要新判据的，而那是
检测器那一侧的活（见下面的不支持清单）。所以这一页只把两类**分开列**，不合并成
一个数去暗示一个它证明不了的结论。

页面上有一段专门写着这件事，`tests/test_api.py` 里有一条测试钉着那段话
（`test_metrics_page_does_not_call_the_rate_an_agent_grade`）——措辞是这一页的
承重墙，改掉它不会有别的东西变红。

## 二、分母

```
预期达成率 = 通过 ÷ (通过 + 不通过)
```

**分母里没有"没有结论"的那些运行**，页面上它们单独占一格。

三类运行分得开，是因为 `TestRun` 上那两个字段本来就是分开的（见 `docs/ui.md`
第 3 条）：`status` 说的是执行（跑完了 / 崩了 / 被熔断），`verdict_ok` 说的是判定
（通过 / 不通过），而 `verdict_ok` 是**可空**的——NULL 表示没留下结论。

这一页的分类只读 `verdict_ok`，**一次都不读 `status`**。理由是量过的：`loop`
场景里被熔断杀掉的运行 `status="killed"`，而它是**通过**的（检测器报出来了、
看门狗动手了，那正是场景想看到的东西）。按 `status` 分类的话，一条通过会被算成
一个失败。`tests/test_metrics.py::test_a_killed_but_passing_run_counts_as_passed`
钉的就是这件事。

"没有结论"的那一格按 `status` 原值拆开（`completed` 几条、`running` 几条），
**原值，不重新归类**——多出来的状态原样出现，而不是掉进一个「其他」里消失。

那一格为什么不能并进分母：把没结论读成"不通过"，等于替一条没有结论的运行编一个
结论出来——本工具最想避免的失效方式。反过来把它读成"通过"更糟。所以它两边都不
算，只被数出来。

## 三、不通过的原因

"不通过"在运行列表里长得一模一样：一个红叉。而它背后是四种不同的毛病：

| 原因 | 判据（报告里那一项） | 这句话在说什么 |
|---|---|---|
| 没跑到能判定的地方 | `error` 非空，或者 `expectation` 为 null | 结论说的是引擎自己，不是被测对象 |
| 前提不成立 | `premises_held` 为假 | 脚本没被走完，或世界的时间没走对；检测器是在一段不成立的轨迹上下的结论 |
| 目标系统侧的扣款对不上 | `charges_ok` 为假 | 地面真值：钱扣了几次 |
| 预期未达成 | `expectation.missing` 或 `.unexpected` 非空 | 见上一节 |

三条口径：

* **一次运行可能同时占好几行**（执行崩了，预期自然也没达成），所以各行相加会
  大于不通过的条数。这句话写在页面上——那几行数字看起来像是可以相加的。
* **不判"哪个原因更要紧"。** 那需要业务语义，是场景声明的事。
* **读不出来的单独一行，不猜。** 报告没留存（老运行），或者留存的那份缺了判
  `ok` 要用的字段，这条运行就不进任何一行原因——按缺的那项反推原因就是替一条
  没有证据的运行编理由。它单独出现在「原因读不出来」那一行。

## 四、延迟

五个口径，**不合并**：

| 那一行 | 量的是什么 | 边界 |
|---|---|---|
| 模型调用（非流式） | 请求发出 → 收到完整响应 | 网关侧 |
| 模型调用（流式） | 请求发出 → **最后一帧** | 网关侧；"一次"的含义与上面不同 |
| 工具调用 | 出口代理 → 目标系统的往返 | **不含看门狗的时间** |
| 其中：看门狗 | `watchdog.enforce` 一次的耗时 | **我们自己的开销**；只算跑过的调用 |
| 运行墙钟 | 运行登记 → 执行收尾 | **不含检测器与报告**，含看门狗 |

* 流式与非流式不合并，因为 `LlmCall.streaming` 这两个值下 `latency_ms` 的含义
  不同（见 `db/models.py`）。把它们平均到一起会得到一个没人定义过的数。
* 工具调用那一行**不是"Agent 等这个工具等了多久"**：`latency_ms` 在出口代理的
  看门狗 `enforce` 之前就量完了，而看门狗是在这个请求里同步跑的。
* **「其中：看门狗」是"谁的错分开写"那一栏。** 看门狗是在出口请求里 `await` 的，
  而 Agent 正阻塞在那个请求上等它扫完——这笔时间记在**被测会话的墙钟**上。它原先
  在轨迹里看不见，于是一次"因为我们太慢而超时"的运行和一次"Agent 自己慢"的运行，
  报告上长得一模一样。账记在 `ToolCall.watchdog_ms` 上（按调用存，不按运行存一个
  总数：代价随调用次数超线性涨，只有落在被叫的那一次上才分得开）。
* **那一行只统计跑过看门狗的调用**，页面同一段话里给出"有 N 次调用没跑到"（被边界拦下的，或者这一列加出来之前的行）。被边界
  拦下的调用（未声明的工具、走错入口、出口被拒、参数不合 schema）在目标系统上什么
  都没留下，看门狗不为它们扫——**`NULL` 不是 `0`**：0 说的是"跑了，快到量不出来"。
  混起来，中位数会被一批压根没测过的调用拉低，而那一行看起来完全正常。
* 运行墙钟是**真实时间**——长时运行的世界时间是另一根钟（`docs/longrun.md`），
  它不拨 `started_at` / `completed_at`。**它含看门狗**（那笔时间发生在请求里，
  跑不掉），所以"我们的开销占了多少"要看上面那一行，不能从这里减。

### 报中位数，不报平均

一次被超时强杀的工具调用（默认 180 秒）能把平均拉到一个任何一次真实调用都没见过
的数，而那个点恰恰是最该看见的——被平均掉了。所以报两个数：

* **中位数** = 通常多快；
* **最大** = 最坏多慢。

取值方法写死：偶数个取靠上的那一个，不取两个的中间值。中间值会造出一个没有任何
一次观测取过的数，而这一页报的每个数都该是量到过的。

表格里那一列叫**样本**，是这一批里的**调用次数**，不是运行次数。0 表示这一批里
一次都没有，不是"耗时为 0"。

## 五、所有栏位取的是同一批运行

范围是「最近 N 次」，N 可以在页面上切（20 / 50 / 200，默认 50）。**结论、原因、
延迟、成本都是这一批的。**

成本那一格不是 `cost.by_scenario()` 那种全量口径：一个按"最近 N 次"算、另一个按
全量算的话，页面上两栏说的就不是一回事，而它们看起来同样正常。成本页
（`/cost`）回答的是长期问题，那一页有自己的入口。

地址栏里那个 `limit` 会被收进 `[1, 200]`：这一页每次都要把 `report_json` 拉回来
解析，不封顶的话 `?limit=1000000` 会把整个库读进内存。`limit=0` 按默认值处理
（多半是参数没填上），不按"只看最近 1 次"——后者会让页面显示一个看起来正常、
实际被截到只剩一条的分布，而"最近一条通过"和"最近 50 条全通过"长得一样。

分场景那张表里，每一行的分母**只含它自己**。用例集一直在变，把不同版本的场景
混进一个总数里，得到的"达成率"没有任何一个场景对得上号。

## 不支持清单（别假装支持）

* **不做趋势。** 这一页只有"最近一批"这一张切片。按天/周/月的趋势在成本页
  （`cost.by_period`）；结论的趋势没做——它需要先回答"用例集变了怎么比"，
  而那个问题还没有答案。
* **"预期没命中"不等于"检测器漏报了"。** 那条推断要脚本消费量，而它现在只是
  报告里的一项数据（`script_steps_consumed`），没有任何一处把它变成结论。
  `scenario/expect.py` 的模块注释写着"这条判断放在 runner 里做"——**那句话目前
  没有对应的代码**（只在前提不成立时印一句说明，不构成推断）。这一页因此只报
  "预期没命中"，把"所以是谁的错"留给读的人。
* **不报 p95。** 本机这个量级（几十次运行）里 p95 基本就等于最大值，并列两个
  几乎一样的数会让人以为它们不同。真要 p95，先把样本量做上去。
* **不判"这批比上批好了没有"。** 那是回归集（`/regression`）的职责：它比的是
  一次运行与一条**冻结的基线**，而基线是有人签字认定过的。看板只陈述分布。
* **不算缓存命中率、成功率之类的派生指标。** 边界上有 `cache_read_tokens` /
  `cache_write_tokens`，但那是成本口径（见 `docs/cost.md`），这一页不重算。
* **"Agent 感知的端到端延迟"没有这个数。** 工具调用那一行不含看门狗，运行墙钟
  含进程启动与会话调度——两处都不是"Agent 觉得自己等了多久"，而那个时间只在
  Agent 进程内，边界拦不到（ADR 001）。
