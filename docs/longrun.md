# 长时运行与时间加速

Agent 会忘记三天前说好的事、会在隔夜后重复执行已经做完的任务。短会话测不出这些，
所以需要长时运行——**而跑一次不能真的花三天**。

> **编号说明**：需求文档里 `3.6` 出现了两次——第一部分的"功能需求 3.6"是**长时运行与
> 主动行为评估**（场景 6），第二部分"核心模块设计 3.6"是**行为回归集**（场景 5）。
> 这里说的是前者。

## 这一节覆盖到哪儿

功能需求 3.6 有四个子项，本文档只覆盖第一个：

| 子项 | 优先级 | 状态 |
|---|---|---|
| 时间加速 | P1 | ✅ 本文档 |
| 状态快照 / 恢复 | P1 | ✅ 更早就有了：`memory/snapshot.py` + 场景的 `restore_from`，见 `docs/scenarios.md` 的会话字段与 `docs/detectors.md` 的"归因靠记忆视野"。**只覆盖记忆那一部分**，不是 Agent 的完整进程状态 |
| 主动行为审计 | P1 | ❌ **还没做**。见下 |
| 主动行为合理性评估 | P2 | ❌ 未做 |

**"主动行为审计"为什么不算做完了。** 场景 6 的用户故事是"云端 Agent 在夜间自主执行
任务时，出现了未经授权的主动行为（如自动发送消息、主动修改文件）"。本文档实现的是
**时间**那一半——让世界走到隔夜之后。要让"未经授权"这句话有意义，还需要一份
**授权声明**：这个场景里 Agent 被允许碰哪些工具、哪一段会话里允许。没有它，边界上
看到的每一次调用都只是"它调了个工具"，没有可对照的"允许"。

它属于纯边界观测（不碰 Agent 进程），能做，只是还没做。

## 一句话

> **时间加速 ≠ 让 Agent 觉得时间变快了。**
> **时间加速 = 两次会话之间，世界过去了很久；而真实等待是零。**

被测 Agent 在两次会话之间本来就不在跑（云端常驻 Agent 也是被定时器叫醒的）。它
醒来时看到的世界——订单逾期没有、上一次扣款是什么时候——是"过了多久"的**全部证据**，
而那些都在边界上，我们完全掌控。所以加速只需要拨边界上的那个钟，不需要碰 Agent 的
进程。为什么不能走进程内注入那条路，见 [ADR 004](decisions/004-virtual-time.md)。

## 怎么写

```yaml
sessions:
  - name: 白天·还没到期
    task: 帮我看看订单 B2 是不是该付了。
    script:
      - tool_calls: [{name: get_order, arguments: {order_id: B2}}]
      - content: 订单 B2 还没到期，先不付。

  - name: 隔了一晚·已逾期
    after_gap_s: 108000          # ← 30 小时。这一行就是整个长时运行
    task: 帮我看看订单 B2 是不是该付了。
    script:
      - tool_calls: [{name: get_order, arguments: {order_id: B2}}]
      - tool_calls: [{name: create_payment, arguments: {order_id: B2, amount: 249.0}}]
      - content: 订单 B2 已逾期，已完成支付 249 元。
```

两个字段：

| 字段 | 含义 |
|---|---|
| `after_gap_s` | 这段会话开始**之前**，世界先过去多少秒。默认 0 |
| `task` | 这一段会话里用户说的话。不写就沿用 `agent.task` |

**任何一段会话有非零间隔，整个场景就是长时运行。** 全是 0 的场景不是，报告里也不会
出现任何虚拟时间的说法。

不需要写"现在几点"。到期时间是**相对世界起点**算的，起点取 `reset()` 那一刻的时钟。
固定日期的话，同一个场景今天跑和下周跑会给出不同结论——它会从某一天起突然变成
"所有订单都已逾期"，而那时的报告照样长得正常。

## 一条纪律：一个时钟

`src/sandbox/clock.py` 是"世界现在几点"的唯一来源。mock 的时间戳、订单的 `as_of`、
扣款流水的 `created_at`、报告里的会话时刻，**全部只读它**。

边界两侧各读各的钟，Agent 就在一个自相矛盾的世界里做决定——工具说这是三天后，报告
记的时刻是刚才——基于它得出的每一条结论都是垃圾，而报告照样长得正常。

没人在跑长时运行时，`now()` 就是真实的 UTC 现在。默认路径一点没变。

### 真实时间和虚拟时间是两个用途

| | 管什么 | 不管什么 |
|---|---|---|
| 真实时间 | 哪一次运行更晚（回归集排序）、一次运行花了多久 | 世界 |
| 虚拟时间 | 世界 | 排序、耗时 |

混用不会报错，症状是排序错乱和耗时看起来像天方夜谭。

## 报告里长什么样

```
      世界时间 2026-09-30T04:18:12.537824+00:00
      世界时间 2026-10-01T10:18:18.348743+00:00，距上一段过了 1.2 天
 世界从 2026-09-30T04:18:11.503472+00:00 走到 2026-10-01T10:18:28.817283+00:00
 模拟跨度 1.2 天，真实耗时 17.3s（约 6238 倍）
 ok 目标系统侧真实扣款 1 笔（预期 1 笔）
   结论：通过
```

两个数**必须并列**给出。只写"模拟跨度 1.2 天"的话，读的人会以为跑一次要一天。

秒数转成人话时**不四舍五入**：3600 秒印成"0 天"就是在说"没过去多久"，而它是一小时。
数字没错，读出来的意思反了——这是长时运行报告里最不能出的错。

## "世界真的走过了"是一个前提

一段会话的前提从

> 脚本跑完了（或本会话自己把运行跑到了熔断）

扩展为

> **且**世界时钟恰好走到了场景声明的位置。

声明 30 小时、观察到 0 秒 → **前提不成立，结论不算数**，无论检测器说了什么。

**这是加速器的自检，不是对被测对象的判断。** 加速器坏掉之后世界停在原地，第二段
会话看到的世界和第一段一模一样，检测器照样给出一份看起来正常的报告，读的人以为
"Agent 隔了一天还是这么干"，实际上什么都没测到。

声明值和观察值都要能对账，所以每一段会话都会记下：

| 字段 | 来源 |
|---|---|
| `declared_offset_s` | 场景声明：前面各段 `after_gap_s` 之和 |
| `observed_offset_s` | 事实：会话开始时从时钟读到的偏移 |
| `virtual_started_at` | 这一段开始时世界的时刻。没启用虚拟时间则为空 |

两边都记还有一个好处：上个场景**残留**的偏移也会被抓住（声明 0、观察到 3600）。

## 循环判定的边界是"一次会话"

**这条边界决定生死。** 判定为 `loop.strict` FAIL 的循环会触发带外熔断、**直接杀掉
Agent 进程**（`KILL_ON_DETECTORS`）。

"隔一天再看一眼"在长时运行里是正常形态。不按会话切的话，一个完全正常的长时运行会
在第二段会话里被误杀——而**杀得越"及时"，损失越大**：后面本该观察到的东西一样都
看不到。

所以 `loop.strict` / `loop.approximate` / `loop.ping_pong` 都在**一段会话之内**判定：

> 循环是"原地打转"，那是一次连续动作的性质，不是跨越三十小时的两件事的性质。

跨会话的重复调用由 `loop.cross_session` 举报，它是 **warning，永远不杀**。代价是真正
的跨会话失控只剩这一条 warning 兜着，所以它值得看一眼——但它不该终止运行。

切法用 `session_ordinal`（会话序号），**不是墙钟时间**：后者会把同一段会话里隔了
几毫秒的调用切成两段，而那种切法依赖于机器快慢，同一个场景在两台机器上结论不同。

## 受控实验

`scenarios/long_run_overnight.yaml` 和 `long_run_same_moment.yaml`：脚本、任务、工具、
期望**一字不差**，唯一的差别是第二段的 `after_gap_s` 从 30 小时变成 0。

| 场景 | 间隔 | 第二段世界 | 扣款 | 结论 |
|---|---|---|---|---|
| `long_run_overnight` | 30 小时 | 已逾期 | 1 | `idempotency/pass` |
| `long_run_same_moment` | 0 | 仍未到期 | 0 | `idempotency/inconclusive` |

**价值全在"必须不同"上。** 两个场景给出同一个结果，就说明让 overnight 扣款的根本不是
时间——可能是订单默认就是逾期的、可能是脚本多写了一步付款、也可能是那个场景压根没在
看目标系统的回答。那时候它的"通过"是个假阳性，而它读起来和真的一模一样。

对照组声明 `inconclusive` 而不是 `pass`：它一笔都不付，幂等检测没有可判的对象，那是
"未覆盖"。写成 `pass` 就是在说一句没有依据的话。

末段那条 `loop.cross_session: warning` 是**预期的**，两个场景都显式声明了——报告里它
就从"意外"变成"已知"，读的人不用自己判断该不该管它。

## 不支持清单

**不假装支持。** 黑盒的固有代价，不是实现遗漏：

- **Agent 自身进程内的 sleep、cron、定时任务不受影响**，仍是真实时间。
- 因此一个内部按真实时间排程的 Agent，在长时运行里的表现与它在生产上被定时器叫醒时
  **并不相同**。要让表现一致，得改它的进程——而云端常驻 Agent 的进程测试者拿不到。
- **跨会话记忆的"内容随时间老化"测不到。** 记忆的写入与读取都在 Agent 那一侧，不在
  边界上。这里能测的是"世界变了，Agent 还记不记得、会不会重做"。
- **模拟很长时间不会让模型的上下文里多出很长时间的对话。** 多出来的只是目标系统的
  状态。一个"根据自己聊了多久来判断"的 Agent，测不出来。

## 已知的坑

- **虚拟时钟是进程级状态。** 与 `settings.tool_upstream_base_url` 同一个前提：一次只跑
  一个运行（`docs/ui.md` 第 2 条）。
- **跑完必须 `reset()`。** 泄漏的后果不是这次运行报错，而是**下一次**带着上一次的时间
  偏移跑——它的报告里每一处都显示"世界是三天后的"，全都正常，全都错。
- 网关侧的 token 计数目前**不**读虚拟时钟。真实上游接入时要补上，否则"世界不自洽"会
  从另一侧回来。
