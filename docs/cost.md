# 成本统计与长期预算预警

需求场景 4。用一句话说清它和网关那套 token 上限的分工：

| | 管什么 | 超了会怎样 |
|---|---|---|
| `gateway/budget.py` | **单次运行**的 token 上限 | 熔断，进程被杀 |
| `cost/aggregator.py` | **跨运行**的累计花费 | 只在报告里说，什么都不拦 |

云端常驻 Agent 的成本失控不会发生在一次运行里。用户故事是"夜间持续运行，
成本是预期的 3 倍"——那是"这个月已经烧掉多少"的问题，得跨运行才问得出来。

```bash
.venv/Scripts/python.exe scripts/cost_report.py               # 按天
.venv/Scripts/python.exe scripts/cost_report.py --period month
.venv/Scripts/python.exe scripts/cost_report.py --json
```

单次运行的成本随场景报告一起出，不用另外查。

## 三条约束

### 1. 一律从明细重算，不信累计字段

`TestRun` 上有 `total_cost_usd`，但那是运行结束时写一次的快照。拿它做长期聚合的话，
任何一次漏结算（网关崩了、进程被熔断杀掉）都会**永久**留在账上，而且和明细对不上。
这种不一致极难发现——两边都是"看起来正常的一个数"。

`LlmCall` 明细是唯一的真相源。`for_run()` 每次现算。

### 2. Token 计数以网关为准，不看 Agent 上报的 usage

需求原文第 1 步写的是"在 Trace 采集层捕获每次 LLM 调用的 `usage_metadata`"，
**这里故意不照做**。`usage_metadata` 来自被测 Agent 的进程，是被测对象能改的东西。
用被测对象自报的账去算它的成本，等于让它自己写考卷。

网关在转发响应时自己数。这条在 W1–W2 就定下了（见 `db/models.py` 里 `LlmCall`
的注释），成本聚合只是沿用。

### 3. 预算状态不是检测结论

`budget_status()` 的结果进报告，但**不进 `findings`**，也不参与 `ok` 的判定。

理由是范畴不同：findings 回答"**这次运行的行为**有没有缺陷"。"本月超支"和被测
Agent 这一次做没做错事没有任何关系。混进去的后果是一次完全干净的运行因为上个月
跑太多而报 `fail`——正是这个项目一直在防的那类错误：把两件不同的事压成同一个
结论，读报告的人无法分辨。

所以它是报告里的独立一节，和"目标系统侧真实扣款"一样：只陈述，不裁决。

## 未定价 ≠ 免费

定价表（`gateway/pricing.py`）里没有的模型，成本按 0 计。**这是最容易出错的
地方**：`$0.0000` 和"我们一个字都没算"看起来完全一样。

所以 `CostRollup.unpriced_calls` 会把未定价的调用数一路带到报告里：

```
--- 成本（陈述，不参与通过与否）---
  3 次 LLM 调用，1,033 in / 55 out，$0.0000
  **注意：其中 3 次调用的模型不在定价表中，成本按 0 计。上面的金额是下界，不是账单。**
```

只要有未定价的调用，金额就标成**下界**。不这么做的话，用户会在收到真实账单时
才发现，而那时已经调了好几轮参数了。

判定价与否是在**查询时**做的，不是落库时存的标志——补一条新模型的单价之后，
历史数据立刻跟着被重新定价。"我们有没有这个模型的单价"本来就该是当下的属性。

## 周期怎么切

| 粒度 | 边界 | 为什么 |
|---|---|---|
| `day` | UTC 零点 | — |
| `week` | **周一** | ISO 周。按周日切的话，周一早上看到的"本周花费"里混着上一个周末的账 |
| `month` | 自然月 1 号 | 不做 30 天滚动窗口。"这个月花超了吗"问的是自然月 |

**归期用 `TestRun.started_at`，不是 `LlmCall.ts`。** 一次运行整个算在它开始的那个
周期里。按调用时间戳归期的话，跑过零点的运行会被劈成两半，两边的数都对不上任何
一次运行——而对不上账的账单比没有账单更糟。

## 开预算

默认全部关闭（`0` = 不设限）。在 `.env` 里配：

```bash
SANDBOX_COST_BUDGET_DAILY_USD=5
SANDBOX_COST_BUDGET_WEEKLY_USD=25
SANDBOX_COST_BUDGET_MONTHLY_USD=100
```

**默认关掉是刻意的。** 一个没配过的阈值一旦生效，就会在别人第一次跑的时候弹出一堆
他不认识的告警——而告警一多就会被整体忽略，包括真正要紧的那些。

正好花完不算超（判据是 `>` 不是 `>=`）。预算写 5 块的意思是"最多花 5 块"，把用满
报成超支会让人以为自己算错了账。

## 没做的：按工具拆解

需求 3.5 要求"按 Agent、工具、场景维度拆解成本"。Agent 和场景做了，**工具没做**，
因为做不出一个诚实的版本：

工具调用本身不花 token——它是打到出口代理的 HTTP 请求。token 花在 LLM 调用上。
想按工具归集，只能沿时间线把"产生这次工具调用的那次 LLM 调用"配上去，而那是个
近似，并且近似得不对：工具**返回的内容**会留在上下文里，让之后每一次 LLM 调用都
继续为它付钱。

所以"这个工具的 token 成本"没有一个单数答案——它取决于工具返回了多大一坨、以及
后面还聊了多久。硬报一个数出来，用户会拿它去做取舍（"这个工具太贵了，换掉"），
而那个数是错的。

真要做，方向是**上下文占用**而不是"调用开销"：量每次工具返回把上下文撑大了多少，
再乘上剩余轮次。那是另一个模块，不是这个的一个字段。
