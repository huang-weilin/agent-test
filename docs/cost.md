# 成本统计与长期预算预警

需求场景 4。用一句话说清它和网关那套 token 上限的分工：

| | 管什么 | 超了会怎样 |
|---|---|---|
| `gateway/budget.py` | **单次运行**的 token 上限 | 熔断，进程被杀 |
| `cost/aggregator.py` | **跨运行**的累计花费 | 只在报告里说，什么都不拦 |

云端常驻 Agent 的成本失控不会发生在一次运行里。用户故事是"夜间持续运行，
成本是预期的 3 倍"——那是"这个月已经烧掉多少"的问题，得跨运行才问得出来。

```bash
.venv/Scripts/python.exe scripts/cost_report.py               # 按天
.venv/Scripts/python.exe scripts/cost_report.py --period month
.venv/Scripts/python.exe scripts/cost_report.py --json
```

单次运行的成本随场景报告一起出，不用另外查。

## 三条约束

### 1. 一律从明细重算，不信累计字段

`TestRun` 上有 `total_cost_usd`，但那是运行结束时写一次的快照。拿它做长期聚合的话，
任何一次漏结算（网关崩了、进程被熔断杀掉）都会**永久**留在账上，而且和明细对不上。
这种不一致极难发现——两边都是"看起来正常的一个数"。

`LlmCall` 明细是唯一的真相源。`for_run()` 每次现算。

### 2. Token 计数以网关为准，不看 Agent 上报的 usage

需求原文第 1 步写的是"在 Trace 采集层捕获每次 LLM 调用的 `usage_metadata`"，
**这里故意不照做**。`usage_metadata` 来自被测 Agent 的进程，是被测对象能改的东西。
用被测对象自报的账去算它的成本，等于让它自己写考卷。

网关在转发响应时自己数。这条在 W1–W2 就定下了（见 `db/models.py` 里 `LlmCall`
的注释），成本聚合只是沿用。

### 3. 预算状态不是检测结论

`budget_status()` 的结果进报告，但**不进 `findings`**，也不参与 `ok` 的判定。

理由是范畴不同：findings 回答"**这次运行的行为**有没有缺陷"。"本月超支"和被测
Agent 这一次做没做错事没有任何关系。混进去的后果是一次完全干净的运行因为上个月
跑太多而报 `fail`——正是这个项目一直在防的那类错误：把两件不同的事压成同一个
结论，读报告的人无法分辨。

所以它是报告里的独立一节，和"目标系统侧真实扣款"一样：只陈述，不裁决。

## 未定价 ≠ 免费

定价表（`gateway/pricing.py`）里没有的模型，成本按 0 计。**这是最容易出错的
地方**：`$0.0000` 和"我们一个字都没算"看起来完全一样。

所以 `CostRollup.unpriced_calls` 会把未定价的调用数一路带到报告里：

```
--- 成本（陈述，不参与通过与否）---
  3 次 LLM 调用，1,033 in / 55 out，$0.0000
  **注意：其中 3 次调用的模型不在定价表中，成本按 0 计。上面的金额是下界，不是账单。**
```

只要有未定价的调用，金额就标成**下界**。不这么做的话，用户会在收到真实账单时
才发现，而那时已经调了好几轮参数了。

判定价与否是在**查询时**做的，不是落库时存的标志——补一条新模型的单价之后，
历史数据立刻跟着被重新定价。"我们有没有这个模型的单价"本来就该是当下的属性。

## 估的 token 数：另一件必须报出来的事实

上面那一段管的是"我们没有这个模型的单价"。还有一件长得像、其实是两回事的：
**这一次调用我们根本没拿到上游的用量**。

它发生在这两种情况下：

- 流式请求没带 `stream_options: {"include_usage": true}`。真实上游只有收到这个
  开关才会在流末发一帧带 `usage` 的（`choices` 为空的）帧。网关会替调用方补上
  这个开关，并在响应头 `X-Sandbox-Stream-Options-Added` 里说明它补了；
  调用方明确写了 `false` 时照它的来——那是显式表态，不覆盖；
- 流被中途断开（客户端走了、上游断了），usage 帧根本没到那一步。

这两种情况下 token 数是**网关按看到的内容估的**：输入沿用预扣时那份估算，输出按
转过去的正文与工具参数分片数出来的字符数。调用落库时 `LlmCall.status` 是
`usage_estimated`。

**为什么不能干脆记 0。** `settle` 的语义是"退回预扣、加上实际"，实际传 0 等于把
预扣**全额退回**。一次跑飞了的流式循环会因此一分钱都不算——报告显示这次运行很便宜，
Token 上限永远不会触发，而所有数字看起来都正常。这正是 `budget.py` 里那句
"估多了只是提前熔断（可恢复），估少了会让超限的那一次已经花出去"要防的事。

两个标记各说各的，**不要合并**：

| 标记 | 说的是什么 | 数字往哪个方向偏 |
|---|---|---|
| `cost_is_lower_bound` | 有调用没单价，金额少算了一部分 | 只会更贵 |
| `tokens_are_estimated` | 有调用的 token 数不是上游给的 | 可能偏大，也可能偏小 |

所以 `tokens_are_estimated` **不是**下界。说成下界，读的人会以为"实际只会更贵"，
而它可能更便宜。报告、运行页、回归对比里这两句话各印各的（列表页上分别是 `*` 和
`†` 两个符号，就是为了不让人把两句读成一句）。

## 账没对平：第三件必须报出来的事实

上面两节说的是"这笔钱算得准不准"。还有第三件，它不属于钱本身，而是**沙箱自己
的账出了问题**：账结了，明细没落。

成本是从明细（`LlmCall`）重算的，而明细是在流式响应的收尾写库的。那次写如果被
取消，明细就少一条；**可结账那一半吃不掉**——`TokenBudget.settle` 是在生成器的
`finally` 里**同步**加的，取消打断不了它。于是"结了几次"和"落了几条"会对不上，
而 2026-10-03 之前**没有任何东西在比这两个数**：

```
流式那支  1 次 LLM 调用，449 in / 20 out，$0.0000
非流式那支  3 次 LLM 调用，1,844 in / 55 out，$0.0000
```

同一份世界、同一段脚本、同样的步数，调用次数必须一样。少的那些就是被取消吃掉的
明细。落库那一半已经改成脱离请求的生命周期（`gateway/stream.py` 里的 `asyncio.shield`
加一张待办名单，运行收尾等它们跑完），但**账对不上的可能性不会消失**（进程被杀、
写库真的失败），所以每次运行结束都对一次账：

`ScenarioResult.unrecorded_llm_calls` = 结账次数 − 明细条数，**有符号**：

| 值 | 意思 | 报告上那句话 |
|---|---|---|
| `0` | 比过了，对上了 | 不说 |
| `> 0` | 有调用的账结了、明细没落 | 次数和金额都**少算**了这几笔，是下界 |
| `< 0` | 明细比结账次数多 | 这几行算得比落库还早，实际只会更多 |
| `None` | **没对过账**（老版本写的报告里没有这一项） | 「本次运行没有对账」，上面的数可能少算 |

`None` 不是 `0`：零是"比过了、对上了"，`None` 是"根本没比过"。把后者印成"0 次
缺失"，就是替一个没做过的检查宣布通过——和 `db/models.py` 里那套「NULL 与 0 是
两件事」是同一件事。

三个标记各说各的，别合并（列表页上分别是 `*`、`†`、`‡`）：

| 标记 | 说的是什么 | 数字往哪个方向偏 |
|---|---|---|
| `cost_is_lower_bound` | 有调用没单价，金额少算了一部分 | 只会更贵 |
| `tokens_are_estimated` | 有调用的 token 数不是上游给的 | 可能偏大，也可能偏小 |
| `unrecorded_llm_calls` | 这次运行的**账本身**没记全 | 次数和金额都只会更多 |

**回归对比页是成本出现的第四个地方，那里的规矩略有不同。** 非零的缺口跟着金额
一起标（`$0.0100（明细缺 2 条，金额也少算）`），而 `None` 在那里**不作声**：
对比是在两份报告之间做的，升级前后各跑一次本来就一份有一份没有，那不是"这次比
上次变了什么"，是版本差异——标上去会让每一次跨版本对比都凭空多出一条成本差。

**这个缺口说的是沙箱自己的账，和被测对象做了什么无关**，所以它和上面两条一样是
陈述，不参与 `ok` 的判定。判据在 `tests/test_gateway_stream.py`（含一对受控对照：
流式与非流式各跑一遍同一份脚本，比的是**账**，不只是结论）。

这条链上每一处"拆掉之后谁红"是量过的，不是推的：仓库外的 `_probes/probe_stream_records.py`
一次跑八个方向——拆掉 `asyncio.shield`、不接收尾的 drain、不接对账、把
`reconcile_llm_calls` 折成常数、把报告里那一段的判据写死、把运行页那一段的判据
写死，各看一次谁先红，外加一条只改散文的绿灯对照（**只改散文必须什么都不红**，
不然红的那一支可能只是被自己的改动吵到了）。

## 周期怎么切

| 粒度 | 边界 | 为什么 |
|---|---|---|
| `day` | UTC 零点 | — |
| `week` | **周一** | ISO 周。按周日切的话，周一早上看到的"本周花费"里混着上一个周末的账 |
| `month` | 自然月 1 号 | 不做 30 天滚动窗口。"这个月花超了吗"问的是自然月 |

**归期用 `TestRun.started_at`，不是 `LlmCall.ts`。** 一次运行整个算在它开始的那个
周期里。按调用时间戳归期的话，跑过零点的运行会被劈成两半，两边的数都对不上任何
一次运行——而对不上账的账单比没有账单更糟。

## 开预算

默认全部关闭（`0` = 不设限）。在 `.env` 里配：

```bash
SANDBOX_COST_BUDGET_DAILY_USD=5
SANDBOX_COST_BUDGET_WEEKLY_USD=25
SANDBOX_COST_BUDGET_MONTHLY_USD=100
```

**默认关掉是刻意的。** 一个没配过的阈值一旦生效，就会在别人第一次跑的时候弹出一堆
他不认识的告警——而告警一多就会被整体忽略，包括真正要紧的那些。

正好花完不算超（判据是 `>` 不是 `>=`）。预算写 5 块的意思是"最多花 5 块"，把用满
报成超支会让人以为自己算错了账。

## 按工具拆解：报的是上下文占用

需求 3.5 要求"按 Agent、工具、场景维度拆解成本"。**按工具这一维和另外两维不是一个
东西**，所以它的表头里没有"花费"这一列。

工具调用本身不花 token——它是打到出口代理的一次 HTTP 请求。token 花在 LLM 调用上。
想按工具归集，只能沿时间线把"产生这次工具调用的那次 LLM 调用"配上去，而那是个
近似，并且近似得不对：工具**返回的内容**会留在上下文里，让之后每一次 LLM 调用都
继续为它付钱。所以"这个工具的 token 成本"没有一个单数答案——它取决于返回了多大
一坨、以及后面还聊了多久。硬报一个数出来，用户会拿它去做取舍（"这个工具太贵了，
换掉"），而那个数是错的。

所以报的是**上下文占用**，三个数各有各的口径：

| 列 | 是什么 | 口径 |
|---|---|---|
| 返回体 | 这个工具返回了多少字节（`ToolCall.result_bytes` 的和） | 数出来的 |
| 实测增量 | 这次调用之后第一次请求比之前那次大了多少字节 | 观测 |
| 租金 | 返回体 × 之后同会话里还剩几次请求 | 条件数字 |

**「实测增量」可能为负**，而且那不是 bug：Agent 自己裁过上下文是真实发生过的事
（这一列的实测值里就有）。

**「租金」是条件数字，不是观测。** 它的前提是"返回体在此后每一次请求里原样重发"。
真实情况里 Agent 可能摘要、可能丢历史——所以它印出来的时候必须连着假设一起印。
而且它**只按返回体本身的字节数算**：实测下来每轮增量比返回体还大（JSON 转义与
消息外壳都要算进去），所以租金是**下界**，不是账单。

两个数之差恰好是这个问题唯一诚实的答案：差额就是"它裁没裁"。

### 几条容易被读错的

**一次都没量到的时候印「量不到」，不印 0。** `ToolCall.result_bytes` 是 2026-10-01
才加的列（在那之前存的是返回体正文，见 README 的对照表）。老库里的行这一列是
NULL，而 NULL 和 0 是两件事：0 = 返回了一个空体，NULL = 没有体量记录——这次调用
没出去（被策略挡下、参数不合法、还没发就失败了），或者这一行来自老库。印成 `0 B`
说的是一句更强的话，而说那句话的人在报告上恰好是错的。真的存在没量到的行时，
报告末尾会单独报个数。

**「租金」这一列所有工具加起来**是说得通的（在同一个假设下，每次请求里属于工具
返回体的那部分字节只会被算到产生它的那个工具头上），但**它不占一列**：它不是某
一行的事，放在任意一行旁边都会被读成"这一行的"。所以它以说明句的形式印一次。

**顺序不是因果。** 顺序由 `seq` 决定——它是**运行内的全局单调序号，LLM 调用与
工具调用共用一条时间线**（见 `trace/recorder.py`），所以"这次调用之后还剩几次
请求"是数出来的，不靠墙钟。这个项目的墙钟会被快照恢复和时间加速拨动。分组必须
按 (运行, 会话)：一次长时运行里有多段会话，而上下文是**按会话**从零开始的。

### 密度

字节折 token 用的密度是**这一段范围里实测的**：Σ请求体 ÷ Σ输入 token，且**只算
记录下请求体字节数的那些行**。老行没有这一列，把它们的输入 token 算进分母会把
密度稀释成一个没有含义的数。一条都没量到时，报告只报字节、不报折算——**不猜
一个数**。

量到的那次 `loop_paging_bounded` 是 **3.29 字节/token**。`tests/test_token_estimator.py`
里钉的「中文 JSON」样本是 2.73 字节/token——同一个量级，差约两成。两个数**不是同
一个口径**：那边量的是纯内容，这边量的是整个请求体（还带着 message 外壳和一串英文
键名），每 token 的字节数本来就会更大。差两成不奇怪，**但也不能拿一个去核另一个**。

### 出口

| 出口 | 怎么给 |
|---|---|
| 场景报告 | `--- 成本 ---` 里一节，正文在 `formatting.tool_cost_lines` |
| 跨运行报告 | `scripts/cost_report.py`，一节以 `TOOL_COST_TITLE` 为标题，用的是同一份正文 |
| 运行页 | `run.html` 的表，数据来自快照里的 `tool_costs` |
| 成本看板 | `cost.html` 的表，数据是 `/cost` 路由传进去的 `by_tool().to_dict()` |
| JSON | `report.tool_costs` / `by_tool_context`（`ScenarioResult.to_dict()`、`cost_report.py --json`） |

正文只有一份实现，理由和这篇文档开头那些"三处各写一份会漂"是同一条。**两个网页
出口不走那份正文**——它是按终端宽度排的等宽表格，塞进 HTML 里就成了预格式化文本。
它们各自的表由同一份 `to_dict()` 供数（聚合器决定有哪些键、什么顺序），模板只负责
画。

**看板那条路有个坑，改动时别踩回去：** 传给模板的必须是 `to_dict()` 之后的形状，
不能是 `ToolCostReport` 对象本身——`tools` 在对象上是个 dict，Jinja 的
`{% for t in ... %}` 遍历 **dict 得到的是键**（一串工具名字符串），于是整张表每一格
都取不到值、静默印成空白，而且不报错。`to_dict()` 把它摊成按租金降序的列表。
这条有探针钉着（`_probes/probe_cost_by_tool.py`）。
