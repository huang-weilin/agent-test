这个数不叫「Agent 合格率」

它答的是「这次运行的结果和场景里写下的预期一致吗」，不是 「这个 Agent 行不行」。一次未达成有两种方向相反的成因：出现了没被任何预期 覆盖的 fail 结论（多半是被测对象做了一件我们没料到的事），或者预期没命中 （多半是我们预料它做的那个错没出现——那往往说明用例要改， 或者检测器漏报了）。从运行记录里分不出"Agent 真的没犯错"和"检测器没报出来"， 所以这里只报"预期达成"，并把两种成因分开列在下面。

口径样本中位数 最大边界

报的是中位数不是平均。 一次被超时强杀的工具调用（默认 180 秒） 能把平均拉到任何一次真实调用都没见过的数，而它恰恰是最该看见的那个点—— 被平均掉了。中位数看"通常多快"，最大值把长尾摆出来。
工具调用那一行不是"Agent 等这个工具等了多久"：latency_ms 在出口代理的看门狗 enforce 之前就量完了，而看门狗是在这个请求里 同步跑的——所以那段时间记在 Agent 的墙钟上、而不在那一行里。 它单列成下面那行的理由就是"谁的错分开写"：一次"因为我们太慢而超时"的运行， 原先和一次"Agent 自己慢"的运行在报告上分不开。
「其中：看门狗」只统计跑到看门狗上的那些调用（ watchdog_ms 非空），这一批里有 {{ report.latency.calls_without_watchdog }} 次调用没跑到—— 被边界拦下的调用在目标系统上什么都没留下，看门狗不为它们扫；这一列加出来之前 落的行也在这里（那时没量过，补不出来）。见 docs/detectors.md。没跑到不是 0，所以没并进那一行。
"样本"是这一批里的调用次数，不是运行次数——0 表示这一批里 一次都没有，不是"耗时为 0"。
